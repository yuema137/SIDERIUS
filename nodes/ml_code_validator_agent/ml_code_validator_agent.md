# MLCodeValidatorAgent

> 8 deterministic checks + 1 LLM code-review + 1 conditional inheritance check for agent-generated PyTorch model plugins. Combines deterministic checks (plugin loads, tests pass, description valid, scalar-only config, forbidden-pattern AST scan, in-process instantiation + gradient flow + output-type) with one LLM code-review call (spec alignment + trainability + implementation issues). Decides whether the implementor's output is ready for the downstream tuner.

## Position in the pipeline

- **Node type**: **standalone-capable** — `nodes/ml_code_validator_agent/ml_code_validator_agent.py` exposes a CLI `main()` that takes every required artifact via explicit args (file paths + config + spec + description), builds a `ValidatorInput`, runs the 8-check pipeline, and writes `validation_{run_name}.json` to the workspace.
- **Upstream**: `ml_model_implementor` (provides `model_type`, `model_file_path`, `test_file_path`, `description_file_path`, `config_fields`, `model_description`, `mathematical_definition` via the `ml_model_impl_to_ml_model_valid` protocol — plus `inherited_components` from the original proposal that get carried through).
- **Downstream**: `ml_hyperparameter_tune_agent` — the workflow gates on `ValidatorOutput.passed`; only validated plugins reach the tuner. The validator's `expert_advice`, `spec_deviation_notes`, and `inheritance_deviation_notes` propagate forward as soft signals.
- **Protocol (upstream)**: `ml_model_impl_to_ml_model_valid` — maps `ImplementorOutput.{model_type, model_file_path, test_file_path, description_file_path, config_fields, model_description, mathematical_definition, model_io_contract}` into this node's `ValidatorInput`. `model_io_contract` (Step 04a) is the normalized Step-03 Model-I/O declaration the candidate was generated against; it is mapped verbatim and never re-resolved here, so the validator probes against the same declaration the implementor used. `inherited_components` flows from the original `ProposalOutput` through the chain state.

## Input

**Schema**: `ValidatorInput` in `agent/schemas/validator.py`

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `model_type` | `str` | Yes | — | The `PLUGIN_MODEL_TYPE` key to validate. Same as the upstream implementor's `model_name`. |
| `model_file_path` | `str` | Yes | — | Absolute path to the plugin file written by `ml_model_implementor`. Read for the deterministic + AST + in-process + LLM-review checks. |
| `test_file_path` | `str` | Yes | — | Absolute path to the test file written by `ml_model_implementor`. Run via `pytest` as a subprocess in check #2. |
| `description_file_path` | `str` | Yes | — | Absolute path to the description.md written by `ml_model_implementor`. Existence + length validated in check #3 (>50 chars). |
| `config_fields` | `dict[str, Any]` | Yes | — | Config field names and their default values, as generated by the LLM. Used in check #4 to verify all fields are scalar (`int`, `float`, `bool`). |
| `model_description` | `str` | Yes | — | Plain-English description of the architecture from the proposal. Passed to the LLM reviewer (check #8) so it can assess spec alignment. |
| `mathematical_definition` | `str` | Yes | — | Precise mathematical/architectural specification from the proposal. Passed to the LLM reviewer to verify the implementation matches the spec. |
| `llm_provider` | `Literal["gemini", "openai", "deepseek"]` | No | `"gemini"` | LLM provider for the code review step (check #8). |
| `llm_model_id` | `str` | No | `"gemini-3.1-flash-lite-preview"` | Specific model ID passed to the provider for code review. |
| `expert_advice` | `str \| ExpertAdvice` | No | `""` | Structured guidance from upstream agents or orchestrators. Accepts a plain string or a structured `ExpertAdvice` object. Injected into the LLM-review prompt as context. |
| `human_advice` | `str \| None` | No | `None` | Optional human-provided guidance — **highest priority**, overrides `expert_advice` when present. Injected into the LLM-review prompt as high-priority context. |
| `inherited_components` | `list[InheritedComponent]` | No | `[]` | Claimed architectural primitives from the `DiscoveryMemo` (carried through from the original `ProposalOutput`). When non-empty, the validator runs check #9 (inheritance regex check) — verifies each claimed component's vocab-seed pattern appears in the plugin source. |

## Output

**Schema**: `ValidatorOutput` in `agent/schemas/validator.py`

| Field | Type | Description |
|---|---|---|
| `passed` | `bool` | **Trainability gate.** `True` only if the model will run and train: plugin loads + tests pass + description valid + config fields scalar + forbidden-patterns clean + in-process instantiation succeeds + gradient flow OK + LLM review's `passed=True`. `inheritance_check_passed` is NOT in this gate (regex checks are too brittle to block a model that otherwise trains; surfaced as a deviation note instead). |
| `model_type` | `str` | The model type key that was validated (passthrough). |
| `plugin_registered` | `bool` | Whether the plugin file loaded and exposes `PLUGIN_MODEL_TYPE`, `PLUGIN_CONFIG_CLASS`, `PLUGIN_MODEL_CLASS`. |
| `tests_passed` | `bool` | Whether all pytest tests in the generated test file passed. |
| `description_valid` | `bool` | Whether `description.md` exists and contains substantive content (>50 chars). |
| `config_fields_valid` | `bool` | Whether all config fields are scalar types (`int`, `float`, `bool`). |
| `forbidden_patterns_check_passed` | `bool` | Whether the plugin source is free of Python loops over the time dimension inside `forward(...)`. AST-based static check — runs even when the plugin failed to import. `False` blocks the trainability gate. |
| `instantiation_passed` | `bool` | Whether the model could be instantiated in-process and the forward pass produced the shape its DECLARED contract requires. Since Step 04a that shape is derived from `ValidatorInput.model_io_contract` (`[1, 256, 64]` under the shipped TIDMAD declaration); with no contract the legacy geometry is used unchanged. |
| `gradient_check_passed` | `bool` | Whether a backward pass succeeded and all trainable parameters received non-`None` gradients. |
| `output_type_valid` | `bool` | Whether `PLUGIN_OUTPUT_TYPE` matches the actual forward output dimensions. The plugin's own declaration selects the FORM and the contract supplies the facts inside it: under the shipped declaration `"classifier"` expects `[B, 256, T]` and `"regressor"` expects `[B, T]`; under a task declaring 16 classes the classifier form becomes `[B, 16, T]`. A `"classifier"` declaration under a task with no class alphabet fails closed rather than guessing a cardinality. |
| `llm_review_passed` | `bool` | Whether the LLM code review concluded the implementation is sound (trainability-only — spec alignment is assessed independently). |
| `inheritance_check_passed` | `bool` | Whether all claimed `inherited_components` were found in the plugin source. `True` when `inherited_components` is empty (check skipped). **Soft-fail** — not in the trainability gate. |
| `inheritance_check_notes` | `list[str] \| None` | Per-component results: which passed, which failed, which were skipped (no pattern in vocab seed). `None` when `inherited_components` is empty. |
| `unverified_inherited_components` | `list[str]` | Names of claimed `inherited_components` whose regex pattern did not match. Structured for downstream consumers (e.g. the interpretation agent treats unverified components with appropriate skepticism). |
| `test_output` | `str \| None` | Full pytest stdout/stderr captured on both pass and fail. |
| `llm_review_spec_alignment` | `bool \| None` | LLM assessment: does the implementation match the mathematical definition? Surfaced separately from `llm_review_passed` because spec deviation does NOT block the trainability gate. |
| `llm_review_trainability_concerns` | `list[str] \| None` | LLM-identified concerns about gradient flow or training stability. |
| `llm_review_implementation_issues` | `list[str] \| None` | LLM-identified correctness bugs or logical errors. |
| `llm_review_notes` | `str \| None` | LLM's brief overall assessment of the implementation quality. |
| `spec_deviation_notes` | `str \| None` | Human-readable summary of how the implementation deviates from the mathematical spec, emitted when the model passes trainability but `llm_review_spec_alignment=False`. Carried forward as a soft signal to downstream nodes. |
| `inheritance_deviation_notes` | `str \| None` | Human-readable summary listing which claimed `inherited_components` could not be verified, emitted when the model passes trainability but the inheritance check failed or had unverified entries. |
| `error_message` | `str \| None` | Human-readable summary of what failed. `None` if `passed=True`. |

## CLI usage

```bash
.venv/bin/python nodes/ml_code_validator_agent/ml_code_validator_agent.py \
    --model_type attn_unet \
    --model_file_path /home/yuema137/SIDERIUS/agent_generated/models/attn_unet.py \
    --test_file_path /home/yuema137/SIDERIUS/agent_generated/tests/test_attn_unet.py \
    --description_file_path /home/yuema137/SIDERIUS/agent_generated/models/attn_unet/description.md \
    --config_fields '{"segmentation_size": 16384, "batch_size": 4, "embed_dim": 32, "num_heads": 4}' \
    --model_description "UNet with multi-head self-attention in the bottleneck..." \
    --mathematical_definition "Encoder: Conv1d(1->32, k=7) -> MaxPool(2) -> ..." \
    --llm_provider gemini \
    --llm_model_id gemini-3.1-flash-lite-preview \
    --workspace ./siderius_workspace \
    --run_name v1
```

The CLI takes every required `ValidatorInput` field as an explicit argument — there is no `--proposal_path` / `--implementor_path` convenience because the validator doesn't look anything up from disk-by-convention; the upstream implementor's output paths + spec strings are all explicit. Result lands at `{workspace}/validation_{run_name}.json` and is also printed to stdout as JSON.

**Limitations of standalone CLI use**:

- **No `inherited_components`** — the CLI has no flag to pass them, so check #9 (inheritance regex) is always skipped in standalone mode. The workflow path is the only way the inheritance check runs.
- **No `expert_advice` / `human_advice`** — fresh review, no upstream guidance.

## Python API usage

```python
from nodes.ml_code_validator_agent.ml_code_validator_agent import MLCodeValidatorAgent
from agent.schemas.validator import ValidatorInput
from agent.schemas.proposal import InheritedComponent
from agent.schemas.storage import StorageConfig, LocalStorageConfig

inp = ValidatorInput(
    model_type="attn_unet",
    model_file_path="/abs/path/to/attn_unet.py",
    test_file_path="/abs/path/to/test_attn_unet.py",
    description_file_path="/abs/path/to/description.md",
    config_fields={"segmentation_size": 16384, "batch_size": 4, "embed_dim": 32, "num_heads": 4},
    model_description="UNet with multi-head self-attention ...",
    mathematical_definition="Encoder: Conv1d(1->32, k=7) -> ...",
    # Inheritance regex check fires when this is non-empty (workflow-only typically):
    inherited_components=[
        InheritedComponent(
            component="spectral_conv",
            source_type="experiment",
            source_id="gated_fno",
            contribution_evidence="Spectral mixing in the bottleneck.",
        ),
    ],
    # LLM-review provider routing:
    llm_provider="gemini",
    llm_model_id="gemini-3.1-flash-lite-preview",
    # Storage for the output record:
    storage=StorageConfig(
        backend="local",
        local=LocalStorageConfig(workspace="./workspace", run_name="iter_001"),
    ),
)

agent = MLCodeValidatorAgent(provider="gemini", model_id="gemini-3.1-flash-lite-preview")
output = agent.run(inp)  # -> ValidatorOutput
```

The constructor accepts `bridge_factory` (test injection — defaults to `LLMBridge`) and `max_retries` (defaults to `None`, infinite quota retry per project policy). Note `provider` and `model_id` on the constructor set the LLM that runs check #8 (code review); `inp.llm_provider` / `inp.llm_model_id` are forwarded into `ValidatorInput` for the same purpose — keep them aligned.

## Storage outputs

- **Validation report JSON**: `{storage.local.workspace}/validation_{run_name}.json` — the validated `ValidatorOutput` dumped at the end of `run()`. Contains every per-check boolean + the LLM review breakdown + any deviation notes. The workflow reads `passed` to gate the tuner; the deviation notes propagate as soft signals.

That's the only file this node writes. No subprocess side-effects beyond the pytest subprocess in check #2 (which writes nothing of its own).

## Key behavioral notes

- **8 deterministic checks + 1 LLM review + 1 conditional inheritance check.** The checks run in a fixed order so a failure earlier doesn't waste later effort:
  1. **Plugin load** — `importlib` the plugin file; verify `PLUGIN_MODEL_TYPE`, `PLUGIN_CONFIG_CLASS`, `PLUGIN_MODEL_CLASS` are all present.
  2. **Tests pass** — run pytest as a subprocess on the test file; capture stdout/stderr regardless of pass/fail.
  3. **Description valid** — `description.md` exists and has >50 chars.
  4. **Config fields scalar** — every value in `config_fields` is `int`, `float`, or `bool`.
  5. **Forbidden patterns** — AST scan rejects Python `for` / `while` loops over the time dimension inside `forward(...)`. Runs even when the plugin failed to import (catches static issues independent of importability).
  6. **In-process instantiation** — build `PLUGIN_CONFIG_CLASS(**probe_config_kwargs(PLUGIN_CONFIG_CLASS))` + `PLUGIN_MODEL_CLASS(config)`, run a forward pass on a probe input and assert the output shape its declared contract requires. Both are built by `agent/skills/model_io_probe_skill.py` from `model_io_contract`: rank, axis order, class cardinality and input dtype are contract-owned, while the batch extent and the realization of a symbolic axis (`T = 64`) are Step-04 probe recipes and deliberately NOT task config.

     The config kwargs come from that same recipe module (C12-P / F-12e-G1). **A generated config class may legitimately declare required fields**, so "`PLUGIN_CONFIG_CLASS()` must succeed with zero arguments" is not a valid generic invariant: since `ml_model_implementor` stopped inventing a `segmentation_size` default, a candidate whose baseline declared no size carries that field as REQUIRED, and check 6 used to reject it here with an opaque Pydantic string before the tuner could state the task's own named refusal. `probe_config_kwargs` returns `{}` for every candidate that declares its own defaults — byte-identical to the previous call — and supplies the probe's symbolic extent only for a framework-template field the class declares required. This node deliberately knows nothing about *which* fields those are: it asks the shared authority and splats. Re-spelling the rule here would recreate the implementor/validator divergence that recipe module exists to prevent.
  7. **Gradient flow** — `loss.backward()` succeeds + all trainable parameters have non-`None` `.grad`.
  8. **LLM code review** — one `bridge.generate(VALIDATOR_REVIEW_SYSTEM_PROMPT, ...)` call. The LLM gets the plugin source, `model_description`, `mathematical_definition`, the pytest output (if tests failed), and the instantiation error (if it failed). Returns a `LLMCodeReview` with `spec_alignment`, `trainability_concerns`, `implementation_issues`, `passed`, `notes`.
  9. **Inheritance regex** (conditional — only if `inherited_components` non-empty AND the plugin file is readable): looks up each claimed component's regex pattern in `agent/schemas/vocab_seed.json`; if a pattern exists, runs it against the plugin source. Components without a pattern are SKIPPED (logged but not failed). Components with a pattern that doesn't match are FAILED.
- **`passed` trainability gate excludes `inheritance_check_passed` deliberately.** Regex checks are too brittle to block a model that otherwise runs and trains — false negatives on legitimate implementations (e.g. a component renamed for clarity) would unnecessarily reject good code. Failed inheritance checks surface as `inheritance_deviation_notes` instead, which the interpretation agent reads as a soft signal to discount unverified component claims.
- **`spec_alignment` is independent of `passed`** for the same reason — a model that deviates from the spec but still trains is still useful (the LLM reviewer's spec assessment is fuzzy and shouldn't gate trainability). The deviation surfaces as `spec_deviation_notes` for downstream consumers.
- **Two failure modes feed into the LLM-review prompt as extra context.** If tests failed, the pytest output is appended to the LLM-review prompt. If instantiation failed, the error message is appended. This lets the LLM ground its review in concrete failure modes rather than reviewing in the abstract.
- **`vocab_seed.json` path** is resolved via `Path(__file__).resolve().parents[2]` — accounts for the post-Step-1 `nodes/<agent>/<agent>.py` layout. Future moves of this file would need to update the `parents[N]` count.
- **Test-import behavior** — the `_check_plugin` helper uses `importlib.util.spec_from_file_location` with a unique module name (`_validator_plugin_load`) to avoid stomping on the real `MODEL_REGISTRY` namespace. The plugin is loaded for inspection only, not for registration.

## Dependencies

- **LLM**: exactly one call site per run, via `LLMBridge.generate()` (returns a parsed dict; validated into `LLMCodeReview`):
  - **Code review** — one `bridge.generate(VALIDATOR_REVIEW_SYSTEM_PROMPT, ...)` call per run. System prompt is the module-level `VALIDATOR_REVIEW_SYSTEM_PROMPT` constant. Uses `inp.llm_provider` / `inp.llm_model_id` (note: the constructor's `provider` / `model_id` set up `self.bridge`, which is what actually fires — keep input fields aligned with the constructor args).
- **GPU**: not required. The in-process instantiation + gradient check (#6 + #7) run on CPU with a tiny `[1, 64]` dummy input.
- **External services**: none. The pytest subprocess in check #2 is a local subprocess, not an external service. Filesystem dependencies: reads the plugin/test/description file paths it was handed, reads `agent/schemas/vocab_seed.json` for the inheritance check, writes `validation_{run_name}.json` under the workspace.
