## 1. Background and goal

V18 explores denoising in **split mode**: the 20 TIDMAD validation files
are partitioned into four DataScope groups (`0-3`, `4-9`, `10-14`,
`15-19`), each explored by an independent loss chain and architecture
chain — 8 chains total. Motivation: per-group specialists over the
frequency-band structure, enabled by the `enable_partial_file_list`
feature (DS1–DS8, branch `feat/enable-partial-file-list`), which
enforces the file restriction at the sample-set builder and sandbox I/O
boundary and pins scope + HealthGate policy per workspace via
`run_invariants_lock.json`.

Everything else follows the V17 configuration **unless explicitly
noted**. The exhaustive list of deliberate differences from the V17
launch command (audited flag-by-flag against `reports/v17_20260717.md`
§13):

1. `--data_scope <group>` (new).
2. `--health_gate_files <ALL in-scope files>` (new; V17 had no monitored
   override — YAML defaults `[3,10,17]`).
3. **Seedless cold starts** — V17 passed two full-scope
   `v17_pregate_baseline` seeds; full-scope seeds are incompatible with
   partial scopes and are rejected by ingress validation by design.
4. `--trial_strategy snapshot` omitted (DS7 deprecated warn-and-ignore
   no-op; snapshot is forced under a partial scope anyway).
5. Fresh scope-immutable workspaces named after the run
   (`v18_{flavor}_{AA}_{BB}`) instead of V17's date-suffixed
   `exploration_{flavor}_v17_${DATE}` dirs; run names carry the scope.
6. Screen session names `siderius-v18_*` (V17: `siderius-v17-*-date`).
Everything else is verbatim V17: 20 iterations, `--auto_resume`, 3
rounds, 1 epoch, delta gates 0.0/0.5, budgets 12/120 min + 10/12 GB,
`formal_strategy snapshot`, `formal_round_strategy inherit_best_trial`,
`explore` mode, lit review on, `openai_tiered_v1.json`, observe-mode
HealthGate YAML, V17 advice files, three-branch loss framework.

## 3. Scope / HealthGate contract

- HealthGate policy file: `configs/health_checks_baseline_observe_mode.yaml`
  (observe-only every-round), unchanged on disk. Each chain materializes
  its own `{workspace}/health_checks_effective.yaml` with the run-level
  monitored-file override = **every file in its scope** (operator
  decision, rev 2 — no representative-file selection).
- Scope + gate policy are pinned per workspace by
  `run_invariants_lock.json`; `--auto_resume` validates the lock, and any
  conflicting re-invocation fails at startup before any LLM/training.
- Sampling is snapshot-only under a partial scope (operator config
  errors at startup; LLM plans normalize with recorded provenance), so
  every monitored file has a denoised output every round by construction.

## 4. Seed policy

All 8 chains are **seedless cold starts** (PR #126). The V17 full-scope
seeds are rejected by ingress validation under any partial scope — this
rejection is designed behavior. No seed files are passed.

## 7. Expected output / artifacts per chain

At `{WS_ROOT}/{run_name}/`:

- `run_invariants_lock.json` — resolved scope + `health_gate_enabled` +
  effective-config sha256, written at iteration 1, validated by every
  later iteration/resume.
- `health_checks_effective.yaml` — materialized policy with the
  all-in-scope monitored list (sha pinned by the lock).
- `iter_001/ … iter_020/` — per-iteration `manifest.json`
  (status ∈ completed | no_records | failed, best raw/valid scores,
  `resolved_data_scope` stamp), `iteration_001/{model}/` tuner artifacts
  (`run_output_*.json`, `summary_*.json`, records/), workflow summary.
- `plugins/iter_NNN/` — promoted model/loss plugins for chain resume.
- `.token_run_id`, `token_usage.jsonl` — token audit.
- `/tmp/{run_name}.exit` — exit marker; `{WS_ROOT}/{run_name}_{DATE}.log`
  — full log.

Expected behavior notes: iteration 1 is a cold start (deterministic
"no prior evidence" interpretation, no LLM call for interp); every
record/manifest carries the group's `resolved_data_scope`; `[DATASCOPE]`
banners appear at workflow pre-flight and each tuner startup; the LLM
sees the `[DATA SCOPE]` prompt block and the fixed-params snapshot-only
disclosure; occasional `strategy_normalization_reason=
"partial_data_scope"` provenance is normal, frequent occurrences are not
(disclosure should make them rare — Gate 1 observed zero).

## 8. Monitoring

```bash
screen -ls | grep siderius-v18
tail -60 $WS_ROOT/v18_loss_04_09_${DATE}.log     # etc. per chain
nvidia-smi
df -h /workspace/DATA
for r in v18_loss_04_09 v18_arch_04_09 v18_loss_10_14 v18_arch_10_14; do
  cat /tmp/$r.exit 2>/dev/null || echo "$r still running"; done
# Marker semantics: absent = running/never launched; EXIT=0 = success;
# EXIT=<nonzero> = chain failed; anything else = abnormal. The launcher
# deletes stale markers pre-launch, so a present marker belongs to THIS
# attempt. Note: multiple ${RUN}_${DATE}.log files can legitimately
# belong to one resumed workspace — the newest DATE is the current
# session's log.
# Interim scope-safe peek (read-only, safe on live chains):
.venv/bin/python scripts/v18_wave_summary.py $WS_ROOT/v18_loss_04_09 \
  $WS_ROOT/v18_arch_04_09 $WS_ROOT/v18_loss_10_14 $WS_ROOT/v18_arch_10_14
```

Stop conditions per chain (same as V17): consecutive-failure brake
(3 failed iter manifests → `.chain_halted`), operator `screen -S … quit`.
Resume: rerun the same `launch_v18` line — `--auto_resume` +
`run_invariants_lock.json` validation continue safely.

## 11. Runtime and cost estimate

**Observed evidence (Gate-1 smoke, 2026-07-23)**: `token_usage.jsonl`
records API-reported usage for exactly ONE iteration (real LLM + pseudo
training, `max_rounds=2`): 17 calls, **110,428 prompt + 17,805
completion = 128,233 total tokens** (proposer 54k, tuner 60k,
implementor 12k, validator 2k). This is one iteration's prompt+completion
total — not a per-run or input-only figure.

**Projected V18 production usage (bounded, uncertain)**: V18 iterations
use `max_rounds=3` (tuner portion ≈ ×1.5 → ~160 k/iter baseline) and
later iterations grow (interpretation LLM active after the cold start,
larger histories/vocab/lit-review context — none of which the 1-iteration
smoke exercised). Bounded estimate: **~160–400 k tokens per iteration →
~3–8 M tokens per 20-iteration chain → ~13–32 M tokens for Wave 1**
(input-dominated ~85 %). Dollar cost depends on the openai_tiered_v1
routing mix (gpt-5.4 / mini / nano / deepseek tiers); treat V17's
realized campaign spend as the best prior. A reliable production number
does not exist yet — re-estimate at the Wave-1 checkpoint from the four
chains' `token_usage.jsonl` files (which will be the first
full-campaign ground truth).

**Wall-time ceilings vs expectations**: budgets are per-attempt CAPS,
not predictions. Worst-case ceiling per iteration ≈ 2 trial rounds × 3
attempts × 12 min + 1 formal round × 5 attempts × 120 min ≈ 11 h — never
approached in practice. Expected per-iteration wall time is minutes-to-
tens-of-minutes at 0.02 portions (Gate-2 real-training iterations
completed in ~10–25 min each incl. LLM latency); expect **days, not
hours, per 20-iteration chain**, dominated by formal rounds and LLM
latency. Re-estimate at the resource checkpoint below.

## 11b. Early Wave-1 resource checkpoint (mandatory)

Run ~30–45 min after launch, once all four chains are in their first
active round, and again a few hours in:

```bash
nvidia-smi                       # all 4 procs visible; total VRAM < 63 GB cap
uptime; vmstat 5 3               # load, r-queue, io-wait (wa), swap si/so
free -h                          # available RAM; this box: no swap configured
df -h /workspace/DATA            # growth vs forecast
for r in v18_loss_04_09 v18_arch_04_09 v18_loss_10_14 v18_arch_10_14; do
  echo "== $r"; tail -3 $WS_ROOT/${r}_*.log | head -3; done   # all progressing
.venv/bin/python scripts/v18_wave_summary.py $WS_ROOT/v18_*  # interim peek
```

Actionable thresholds (host: 208 CPUs, 2 TiB RAM, no swap, network FS):
- **STOP/reduce concurrency** if: `wa` (io-wait) sustained > 20 %; any
  chain's log silent > 30 min while others progress (starvation);
  repeated dataloader/subprocess timeouts in any log; VRAM sum
  approaching 63 GB; available RAM < 200 Gi (no swap = OOM-killer risk);
  disk growth > ~50 G/h/chain (cleanup not keeping up).
- **Investigate** if: load average > ~150 (≈ 75 % of 208 CPUs);
  unexpected process multiplication (`pgrep -fc run_one_iteration` > 4;
  each chain spawns ONE runner + transient train/infer/score children).
- Fallback: kill the two `10_14` chains (screen quit), let `04_09`
  finish, then run groups serially — scope-immutable workspaces make
  this safe.
