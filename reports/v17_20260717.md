## 1. Scientific and operational goal

V17 measures, without HealthGate-driven pruning:

- raw exploration performance;
- collapse and invalid-score frequency;
- valid-candidate frequency; and
- the best valid score after collapsed/invalid completed rounds are excluded.

HealthGate is observe-only. Its failures remain completed scientific
observations and do not stop either chain.

## 2. Execution topology and differences from V16

Unchanged from V16:

- two concurrent chains: loss explorer and architecture explorer;
- 20 workflow iterations per chain;
- three tuner rounds per iteration, with the final round formal;
- one epoch maximum;
- snapshot trial and formal strategies;
- 12-minute trial and 120-minute formal time budgets;
- 10 GiB trial and 12 GiB formal VRAM budgets;
- production tiered OpenAI configuration;
- literature review enabled; and
- architecture launch 90 seconds after loss launch.

V17 changes only the evidence, reliability, and guidance layers:

1. explicitly selects the observe-only HealthGate YAML;
2. persists typed HealthGate results and counterfactual production decisions;
3. filters Branch B through the live reusable-loss inventory while preserving
   Option C;
4. uses V17-specific control-variable advice;
5. uses clean post-M9 seed records;
6. persists structured failed attempts; and
7. writes explicit, unique exit markers and checks persisted completion.

## 4. Loss capability contract

- **Branch A**: registered built-in losses.
- **Branch B**: only reusable plugins present in the system-supplied live,
  loadable inventory.
- **Branch C / Option C**: new custom losses with a complete
  `custom_loss_spec`, using the existing proposer → implementor → registry →
  tuner path.

V17 is not built-in-only. A stale, missing, historical, or workspace-only
plugin is not reusable. Loss selection must preserve the selected model's
declared output contract, target representation, inference decoding, and
scoring semantics.

## 8. Raw-versus-valid evaluation contract

V17 execution selectors use the same validity contract: collapsed or
incompletely observed trials cannot be inherited by the formal round, trigger
skip-formal, or bypass the formal time budget. Raw scores remain diagnostic.

The formal comparison reference is fixed at `0.0` for every V17 production
iteration. Therefore the approved `skip_formal_min_delta=0.0` yields a `0.0`
skip threshold and `bypass_formal_time_budget_min_delta=0.5` yields a `0.5`
bypass threshold. The production command does not override this schema value.
V17 does not restore or update a chain-wide incumbent; that committed dynamic
state is deferred to V18.

A completed round is eligible for `best_valid_score` only when:

1. execution completed;
2. scalar score is non-null and finite;
3. required inference/scoring artifacts exist; and
4. every configured counterfactual blocking-style HealthGate check passed.

Routing remains `continue`; validity is a post-run classification. Each chain
summary must report:

- total attempts and attempt failures;
- completed tuner rounds;
- raw best score and its gate status;
- best valid score, iteration, and round;
- HealthGate-valid round count;
- collapsed/invalid round count; and
- valid-round fraction.

If no eligible result exists, `best_valid_score = null`; never substitute the
raw best score. The combined summary reports the same fields across both chains
and identifies the chain owning each raw/valid best result.

## 9. Monitoring and stop conditions

HealthGate failure and model collapse are not stop conditions. Do not add a
repeated-collapse circuit breaker. Intervene only for genuine infrastructure or
orchestration failures:

- repeated CUDA OOM or GPU/driver loss;
- disk exhaustion;
- corrupt or missing input data;
- inability to persist required records/manifests;
- unexpected partial tuner result;
- non-zero exit from a real workflow failure; or
- evidence that the wrong HealthGate config was consumed.

The chains are independent. Collapse or failure in one model proposal does not
stop the other chain. An infrastructure fault affecting the shared GPU should
pause both until its scope is understood.

## 10. Completion verification

For each chain verify all of the following; screen disappearance alone is not
completion:

- unique exit marker exists and contains `EXIT=0`;
- chain/workflow persisted status is complete;
- 20 iteration directories and expected manifests exist;
- every successful iteration's tuner completed its requested three rounds;
- no unexpected partial tuner output is hidden behind a clean shell exit; and
- output paths and required JSON artifacts remain readable.

## 11. Rollback and resume

`--auto_resume` inspects the existing workspace and starts at the next
incomplete iteration. Resume only with the exact timestamped workspace,
run name, merged commit, advice, HealthGate config, and seed policy recorded at
launch. Do not duplicate completed iterations or point a new run at an old
workspace.

Do not resume when the last state is unexpectedly partial, the config/advice
hash changed, persisted records are corrupt, the wrong gate config was used,
or an infrastructure failure remains unexplained. Investigate first, then
resume the same chain independently.

## 12. Runtime and cost estimate

V15 completed two parallel 20-iteration chains in approximately 37.5 hours;
V16 showed more implementation retry and time-gate variance. Assuming one RTX
5090 shared by both chains, unchanged V16 budgets, and similar proposal mix,
budget **36–60 wall-clock hours**, with a long-tail risk near 72 hours. This is
not guaranteed. GPU consumption is roughly 72–120 aggregate GPU-hours if both
chains remain active and serialize substantial GPU work. The final launch Gate
2 consumed **537,319 tokens for only two workflow iterations**. This is evidence
of substantial proposal/retry variance, not a linear full-campaign forecast.
Monitor cumulative token usage after every iteration in both chains and do not
present a falsely precise or low total-cost estimate.
