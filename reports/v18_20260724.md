  priced this at 2.00 ms/step (16 min training, 61.1 min total →
  budget check PASSED); reality was **44.3 ms/step → ≈ 5.9 h**. The
  old global-ceil step resolver was additionally a correctness bug on
  many-small-file scopes (RT1 fixed it; on this config the count was
  already exact).
- **Action**: all four chains intentionally halted; iteration-1

  program was designed, implemented, and gated before any relaunch.

## 2. Runtime-control redesign (what now prevents this)

Landed on `feat/rt1-fixed-step-overhead` (RT1 `788487f` → Gate 2
verdict `1d8775c`). Core principle: **formal execution is admitted only
on a complete, current, measurement-backed prediction of TOTAL runtime
from the actual production environment.**

1. **Exact workload resolution** (RT1): trainer-mirroring per-file step
   resolver (resolves the incident's 480,000 exactly); inference and
   scoring resolvers colocated with their engines.
2. **Static estimator demoted** (RT1): still produced as a prior, but
   schema-enforced `formal_execution_eligible = false` — it can never
   admit a formal attempt again.
3. **In-subprocess measured verification** (RT2): setup measured for
   real; **the first production steps ARE the training verification**
   (adaptive steady-state detection with re-arm, never assumed);
   inference verified the same way with I/O priced separately; an
   in-subprocess rejection consumes an attempt (planner-visible cost).
4. **Observations + priors** (RT2): every attempt writes a live sidecar
   event log and an append-only per-workspace observation store;
   priors are consumed under §6b invalidation (drift eviction N=3, age
   90 d, environment mismatch); rejected/killed attempts stored but
   calibration-ineligible.
5. **Fail-closed total admission** (RT2-E/G): total assembled from
   components under the contribution policy
   (`historical_phase_share_limit = 0.10`); known-cost lower-bound rule
   (Σ predictions × safety factor vs budget); verification failure with
   a budget present → fail closed.
6. **Watchdog** (RT4): process-group deadline kill, deadline =
   `max(floor, min(budget, verified × safety))`, tightened mid-flight
   from the live sidecar; TERM → grace → KILL; clean
   `attempt_failure/wall_clock_timeout` records; proven on a real CUDA
   kill in pre-Gate S3.
7. **Guardrails** (RT5): `max_steps_per_attempt = 150000`,
   `min_formal_batch_size = 4` (the incident shape), explicit
   `allow_extreme_steps` override; guardrail skips are free pre-flight
   (vs in-subprocess rejections, which consume an attempt).
8. **Operator surface** (RT6): `--runtime_watchdog`,
   `--runtime_safety_factor`, `--runtime_watchdog_floor_seconds`,
   guardrail flags — lock-step through schema → protocol → workflow →
   chain runner → shell wrappers, CONTRACT_FLAGS parity-pinned.

## 7. Resource audit (measured 2026-07-24)

Host state at audit: H100 80 GB HBM3 with **0 MiB used, 0 %
utilization**; `/workspace` mount (`mfs`, RunPod network storage)
**239 TB free**; `ulimit -u` unlimited, 524,288 open files; **no

Claude sessions (< 1 core total). No other background workload
competes for the GPU.

**Container limits (the USABLE numbers — this is a RunPod container;
`free`/`nproc` report the bare-metal host and must not be used)**:

- RAM: cgroup `memory.max` = **251 GB (≈ 234 GiB)**; anon (process)
  usage at audit ≈ 2.8 GB, remainder of `memory.current` is
  reclaimable page cache. Exceeding the limit is a kernel OOM-kill,
  so this is the hard ceiling. (The bare host shows 2,015 GiB — not
  ours.)
- CPU: cgroup `cpu.max` = 2210000/100000 = **22.1 effective cores**
  (the kernel exposes 208 host cores; sustained load above 22.1 gets
  throttled).

Measured/code-derived per-chain footprint:

- **GPU**: VRAM budget 16 GB, enforced per attempt as
  `min(live_free × 0.8, budget)` — concurrent chains self-regulate.
  Legacy Wave-1 ran the same four scopes concurrently at 10/12 GB
  budgets with zero VRAM incidents.
- **Host RAM**: chain runner RSS measured 0.5–0.9 GiB across all four
  legacy logs (peak logged 0.89 GiB); training subprocess resident
  footprint is a few GiB (RLIMIT_AS caps are address-space: 40 GiB
  train / 60 GiB inference / 24 GiB scoring; the inference resident
  peak is ≈ 7.4 GiB of numpy per file).
- **CPU**: training DataLoader uses `num_workers: 0` (verified in
  `execute_tools/train_engine_sandbox.py:646` — no worker fan-out; the
  GPU feed is in-process). Scoring uses a `ProcessPoolExecutor` with
  `max_workers = min(8, tasks)` (`execute_tools/scoring_utils.py:602`)

- **Dataset**: snapshot sampling at portion 0.1 → ~120 PSD scoped read
  ≈ 3.6 GB per formal setup (measured in Gate 2-B: 43.7 s warm-cache);
  page cache within the 234 GiB cgroup absorbs repeated reads (cache
  is reclaimable, so it never competes with process memory).
- **Storage**: denoised H5s cleaned per round (`--cleanup_denoised`
  emitted by the chain wrapper); observation stores are per-workspace

### Decision: **2 chains in parallel (Wave 1A → Wave 1B).**

The audit shows four chains fit every hard resource with ≥ 20 %
headroom (VRAM 64/80 tightest, gracefully gated). The operator
decision (2026-07-24) is nevertheless **two-way parallelism**: the
principal residual risk is dynamic GPU *timing* contention, not
resource exhaustion — measured 2.3× inference slowdown under
contention, plus the known post-verification drift limitation (Gate 2
ratio 3.09). Under four-way contention, HEALTHY attempts could exceed
predictions or watchdog deadlines for reasons unrelated to their own
configurations, churning attempts and polluting the prediction ledger
in the campaign's first iterations. Two-way keeps contention mild
while the §2.10 prediction contract accumulates its first production
evidence; four-way remains available for Wave 2 by explicit decision
if Wave-1 ratios come back clean.

## 12. Stop conditions

Stop the affected chain (screen `-X quit`, or the whole active phase)
and report if:

1. Any chain aborts at startup (lock, DataScope, HealthGate violation).
2. A formal attempt runs past its deadline WITHOUT a watchdog kill
   (watchdog malfunction — the incident class recurring).
3. Repeated `wall_clock_timeout` or `rejected_time_risk` on the SAME
   configuration class in one chain (> 2 consecutive) — prediction
   contract broken, do not let attempts churn.
4. GPU free VRAM pinned < 8 GB with attempts VRAM-gated across both
   chains (budget interplay wrong even at 2-way).
5. Container anon memory (`/sys/fs/cgroup/memory.stat` `anon`) above
   ~180 GB of the 251 GB cgroup limit, or sustained CPU near the
   22.1-core quota outside scoring bursts (unexpected fan-out; the
   limit is a kernel OOM-kill, not a soft warning).
6. Any chain writing outside its own workspace, or any read of
