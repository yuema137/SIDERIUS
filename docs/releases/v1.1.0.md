# SIDERIUS v1.1.0

This release makes **working with your coding agent** the main way to use
SIDERIUS. In the Professional or Assistant style, your agent writes the
experiment as a short Python workflow file (`workflow.py`) in your own project,
and you prepare, launch and steer it from the command line. Research loops can
now pause, ask for your advice and resume. Each run records one seed, more LLM
providers are available, and a ready example and a CSV task template give you a
starting point. A task can now **declare how candidates are evaluated**
(meanings, units and a weighted-sum formula), and **pseudo mode** test runs work
on a CPU with no setup. An **experimental browser console** can show, edit and
run the same files.

**Before upgrading:** runs, pseudo workspaces and stored Data Analysis programs
created before v1.1.0 cannot be resumed or reused with v1.1.0; start a new
workspace. Real runs now require an NVIDIA GPU, and several malformed settings
that v1.0.0 silently ignored are now refused. Read
[Changed behavior](#changed-behavior-for-v100-users) first.

A few words used below: an **iteration** is one pass of the research loop
(interpret results, propose a model, implement it, validate it, then train and
tune it). A **tuning round** is one training configuration planned and run inside
Train & tune; trial rounds and the formal round are kinds of tuning round.

## What's new

### Work with your coding agent

- **Professional and Assistant styles.** In Professional style you bring the
  research plan and your agent implements it; in Assistant style you describe
  the problem and your agent guides you through the choices. Both produce the
  same files and use the same commands. The [README](../../README.md#start-with-your-coding-agent)
  has a request to paste for each, and
  [getting started](../getting-started/README.md) gives the ordered setup.
- **Experiments are workflow declarations.** Your agent sets up a task package,
  a `workflow.py` (which research steps run, your advice to each step, training
  budgets, and the loop's iteration limit and stop conditions) and an LLM
  profile. Start from the files in
  [`examples/workflow_declarations/`](../../examples/workflow_declarations/).
  The [workflow declarations guide](../guides/workflow-declarations.md) lists
  what a declaration can set and which features combine.
- **Prepare, then launch.** `python -m tools.candidate_prepare --reusable-request ...`
  prepares a workflow offline and shows what was captured. Nothing is spent
  until you launch it with `python -m tools.candidate_operations submit ...`.
  The same tool reports `status` and `log`, and controls a running loop with
  `stop-loop`, `pause-loop`, `review-loop-resume` and `write-loop-resume`. See
  [Write and run a workflow declaration](../getting-started/README.md#write-and-run-a-workflow-declaration).
- **Setup guidance for your agent.** The
  [setup guidance](../agent-reference/siderius-setup-review/SKILL.md) now covers
  literature reviews merged by an LLM judge, loops that pause for your input and
  resume with an advice file, and how to open a hand-written `workflow.py` in the
  console.

### Research loops

- **Iterations with stop conditions.** A workflow can repeat its research
  iteration up to a set number of times, each one using the previous results.
  Stop conditions (a metric threshold, no improvement for N iterations, an LLM
  judge) end the loop, or, with "pause and ask me" (`on_met="request_input"`),
  pause it and say why.
- **Pause, resume with advice, or end.** Stop or pause a loop between
  iterations and resume the same run, optionally with advice for the next
  iterations (`write-loop-resume --advice-file`). A paused loop can also be
  ended where it is instead of resumed.
- **Recovery after a lost process.** If the process running a resumed loop dies
  before it records its result, the run no longer stays "unknown" and blocks new
  work. Once SIDERIUS confirms that every process has ended, the run is marked
  failed, its finished iterations are kept, and the paused loop it came from
  can be ended.
- **Tuning rounds per iteration.** Train & tune runs at most 10 tuning rounds
  per iteration by default in a workflow declaration (`max_rounds`; the
  `run_one_iteration` CLI default stays 3). The console editor now shows and
  edits this limit, and Run review shows the captured value.
- **See what was tried before you advise.** When a loop pauses for input,
  `review-loop-resume` and the console's pause card list up to the 20 latest
  completed iterations: the proposed model, its validation result, the best
  Health-valid formal score and why tuning stopped (`summary.what_was_tried`).
- **Clear refusals.** A loop on an execution profile that cannot carry one is
  refused with "research loops require the native-interpretation-candidate
  profile".
- **Worked scenario.** The Quickstart examples include a literature review
  merged by debate, followed by a loop that pauses for your input after an
  iteration without improvement and resumes with `write-loop-resume
  --advice-file`.

### Declare how your task is evaluated

A task manifest can now carry an optional `evaluation:` section. Without it,
nothing changes. The [evaluation guide](../guides/evaluation/README.md) walks
through it with the CSV template.

- **Meanings, units and ranges.** Each component's scientific meaning, units
  and range reach every research agent (proposer, interpreter, tuner,
  implementor, validator, literature review, Data Analysis) through one
  rendered block.
- **Weighted-sum selection.** `selection: {kind: formula}` with
  `family: weighted_sum` combines declared metrics, each with fixed
  `lower`/`upper` bounds, into one higher-is-better utility. The framework's
  scoring child computes it; no agent does arithmetic. The utility drives
  ranking, `--target_score`, stop conditions and resume, while Health checks
  keep reading the original metric values. A required term that is missing,
  non-finite or out of range (with `out_of_range: refuse`) makes the candidate
  unscoreable rather than renormalising the other weights.
- **Thresholds name the effective metric.** With a formula, any score threshold
  must name the new effective metric id, because 0.8 utility is not 0.8 of the
  original metric. `--target_score` needs
  `--target_score_metric <effective_metric_id>`, and metric stop conditions must
  use that id. `--enable_chain_incumbent_formal_gates` or
  `--degenerate_penalty_score` also need
  `--score_units_metric <effective_metric_id>`. Formulas run only when the
  task's own metric code scores candidates; an external
  `CandidateEvaluationExecutor` and anchor-normalized scoring are refused.
  `Launch check: admitted` does not test the scoring route.
- **Requirements (feasibility constraints).** `constraints:` entries such as
  `{component: accuracy, op: ">=", threshold: 0.9}` make a candidate that
  violates them, or whose value is missing, not scoreable, with the broken
  constraint named in the record and shown to the agents. Every ranking,
  incumbent, resume, stop condition and adaptor therefore skips it. Trial and
  Formal rounds follow the same rule; Health still reads the original values.
- **Model measurements.** `kind: measurement` components measure the trained
  checkpoint: `trainable_parameter_count`, `total_parameter_count`,
  `model_bytes`, and `inference_latency_ms` (a declared input shape, warm-up and
  repeats, median on the training device). Measurements can be formula terms or
  constraints, for example "fewest parameters with an AUC floor".
- **Rubric guidance.** `kind: rubric` components and
  `selection: {kind: rubric_balance}` give the agents a task-declared,
  natural-language way to weigh results. Rubrics guide the agents; ranking
  stays on the primary metric or the formula.
- **Checked before launch.** Composition validates the section and names the
  offending field, so nothing is silently ignored.

### Pseudo mode test runs

Pseudo mode (`--is_pseudo_llm --is_pseudo_training`) runs the whole loop with
synthetic models and scores, to check a task package and workflow wiring
without cost.

- **No setup.** A pseudo run needs no GPU, API key or memory ceiling
  (`SIDERIUS_SUBPROCESS_RSS_GB`); the run records that no execution envelope
  applies.
- **Follows your task's contract.** The synthetic model takes its output shape,
  floating dtype, output type and loss from the task's Model-I/O contract,
  writes a synthetic deliverable through the task's own writer so Health checks
  run, and produces formula evaluation evidence when the task declares one.
- **Bounded cost.** Unless you set `--validation_max_samples`, a pseudo run
  records an evaluation ceiling of 256 rows, so its cost no longer grows with
  the dataset.
- **Refuses fast.** A task shape the synthetic model cannot produce, or a
  bounded scope that no longer covers the task's Health checks, is refused
  before any work with a typed reason.

  synthetic task and a ready experiment setup. Its `fetch_data.py` now checks the
  bundle's checksums before it runs any task code or writes data, and refuses
  missing, modified or unlisted files. See the
  [example bundle guide](../../examples/console_bundle/README.md).
- The [CSV classification template](../../examples/task_templates/csv_classification/README.md)
  is a complete task package for `train.csv` / `validation.csv` data, with a

### Command line and workflows

- **Run seed.** Each run records one seed, given with `--run_seed` or generated,
  and every training, sampling and validation seed derives from it. A resumed run
  must use the same seed. See the [seed contract](../agent-reference/mechanisms/seeding.md).
- **LLM providers and profiles.** Anthropic, Moonshot/Kimi and Z.AI/GLM are
  available through the optional `pydantic-ai` extra. The opt-in profile
  `configs/llm/openai-moderate-v1.json` is recommended for research runs.
- **Training.** Native training can run explicit cosine or step learning-rate
  schedules (off by default), and epoch caps above 100 are now accepted.
- **Workflow choices.** Conditional routes with a fallback branch; deterministic
  steps that combine, select or distribute results; LLM combining strategies
  (`rubric-rank/v1`, `debate-judge/v1`, `primary-advisors-llm/v1`,
  `judge-merge/v1`); and the judged profiles `native-literature-judged/v1` and
  `native-proposal-judged/v1`, whose judge calls are bounded and recorded.
- **Shared GPU budgets and parallel steps.** Runs can share an operator-declared
  host budget. By default a run that does not fit is refused with
  `host_queue_full`; set `"max_queued_operations": N` in the budget to let up to
  N runs wait in order. Waiting runs no longer load PyTorch. Independent
  workflow steps can run in parallel within the budget. See
  [Share one GPU budget](../../src/tools/candidate_operations/README.md#share-one-gpu-budget-across-operations).
- **GPU runs in the sandbox.** For a task that lists a GPU (`/dev/nvidia<N>`),
  the run sandbox mounts the host's `/sys` read-only and passes the NVIDIA control
  devices automatically, which CUDA needs to start. Tasks without a GPU get
  neither.
- **Untrainable runs are refused before spending.** With trial mode off
  (`is_trial: false`), every tuning round uses single-file mode, which only
  TIDMAD-style tasks can train in. Such a run of any other task is refused, with
  the cause, before any model call. The templates set `is_trial: true`.
- **Custom combining steps** can be checked, self-tested and admitted with
  `.venv/bin/python -m tools.adaptors`; running them inside workflows comes in a later
  release.
- The standard chain launcher accepts `--gpu_execution_policy_json`, so a GPU
  execution policy file reaches every iteration of a chain.
- **`--target_score` counts only Health-valid formal scores.** A score that
  Health rejected no longer stops the workflow. The final JSON summary adds
  `best_valid_formal_score` and `termination_reason` (`target_reached`,
  `iterations_exhausted` or `infrastructure_abort`) and labels
  `best_score_overall` as unfiltered progress.
- **Slowdown floor setting.** `--runtime_verification_pathological_min_unit_ms`
  sets the minimum wall time used by the slowdown check (default 100 ms; `0`
  restores relative-only decisions).
- The CLI reports which `.env` file it loaded and warns when that file is
  outside the checkout, readable by others, or holds an empty key.

### Experimental browser console

The console is new in v1.1.0 and **experimental**: its screens and settings may
change between releases. Use it to see every step once on a small example, or to
view and run a workflow file; check the saved `workflow.py`, not the screen,
when you need to know exactly what runs. You create a private workspace with
`init`, register a task with `add-task`, start the console with `serve` and open
it in a browser, locally or through an SSH tunnel. The
[console first-hour path](../getting-started/README.md#your-first-hour-from-the-example-to-your-own-task)
and the [console guide](../../src/tools/candidate_console/README.md) cover each
step.

On **Run**, step 1 can prepare any saved version of the workflow, not only
the latest; the run records the chosen version's name and SHA-256, and the
file on disk is never changed.

- **Task, experiment setup, run.** Tabs **Home · Task · Workflow · Run · Monitor
  · Settings**. The Task tab summarizes the chosen task (data, model input and
  output with shapes and meanings, classes, task type, objective, main score,
  Health checks, plugins, locked parameters, deliverable). An experiment setup is
  one workflow for one task; each run belongs to one setup and is listed under
  it. The console remembers the setup you last opened for each task.
- **GPU detection.** `add-task` finds this machine's NVIDIA GPUs and gives them
  to the task's runs without asking; `--no-gpu` gives none and
  `--device PATH ...` gives exactly the paths you name. `check --gpu` starts CUDA
  inside the same sandbox a run gets and prints `GPU PASS` or `GPU FAIL` with the
  cause, so you can test a task before launching.
- **Workflow editor.** Build a workflow on a visual canvas from templates or a
  blank start, connect typed inputs and outputs, and review the Python source
  change before saving. Named versions, undo/redo and restore are included.
  **Fit** frames the whole graph; when a large graph cannot fit at the 75%
  zoom floor, Fit frames the selected step instead. The training settings
  explain trial and formal tuning rounds. Saving keeps every value you did not
  edit byte-for-byte (`2.0` stays `2.0`, large integers are not rounded), and
  editing an authored float keeps it a float. Saving an unchanged read-only
  workflow reports "Nothing to save".
- **Template defaults.** Templates start in trial mode, with **Health checks**
  set to Block on failure and **Result standing** set to Scientific, so the
  task's blocking checks can invalidate a tuning round and Health-valid results
  count toward the run's best score. They also set `formal_portion=1.0` and
  `max_rounds=2`: the first tuning round may be a trial, and the last, forced
  formal, trains on the whole training scope. The Train & tune step has a
  **Trial/formal mode** control. A one-round edit that conflicts with trial
  overrides names the remedy (raise **Tuning rounds per iteration** or remove
  the trial overrides).
- **Run and Monitor.** Prepare, review and launch a run, set an optional run
  seed, and follow results, logs and reported token use per model. Run review
  lists the advice, Health mode, training budgets, epoch ceilings, tuning-round
  limit and task locks the run will use, and the setup's run list updates after
  Launch. Failed preparations or launches are named with their cause and log
  file. Monitor shows a **Train & tune outcome** row; a step that completed no
  tuning rounds never reads as succeeded. **Stop run** cancels a running
  candidate. Launched runs keep running if you stop the console server; start it
  again to keep monitoring them. Monitor and the run list share one outcome
  headline (for example "Failed during Propose model … after 1 of 3 completed
  iterations"). A busy Prepare names the operation that blocks it, and a
  preparation whose worker died is released instead of keeping the store busy.
- **Loops in the console.** Stop, pause, resume with advice, and **End loop
  here** for a paused loop, with the reason and what was tried shown when a
  loop pauses. A paused loop can be ended even when its next iteration cannot
  start. The console calls one pass of the loop an iteration everywhere.
- **Settings and credentials.** Choose model profiles, advice files and data
  folders in the browser. The console reads API keys from a mode-600 JSON or
  dotenv file and never prints them; `init` checks only the file's ownership
  and mode, never its contents. Concurrent saves of settings, tasks and setups
  no longer overwrite each other. Light and dark themes are available.
- **Clear errors.** `init`, `check` and `serve` name each invalid
  `console.json` field and the error type (never the value), say whether the
  problem is in `console.json` itself or in the settings it points to, and name a
  missing manifest, model profile or workflow file with its configured path.
  `init` names the exact folder it refuses and why (owned by someone else, or
  writable by group or others). For a folder only you use, it prints
  `chmod 700 <path>`; on a shared HPC folder, it suggests a private subfolder
  (`mkdir -m 700 <path>/siderius`) instead, so collaborators keep their access.
- **Bounded task summaries.** A failing task summary shows a short message, and
  the data-size count stops after five seconds or at other file systems, marking
  the total as partial and saying why.
- **No leaked details in errors.** Task, GPU, setup, settings, import and editor
  errors shown in the browser use fixed messages; the full cause stays in the
  server log for the task author.
- **Run dashboard.** Records with any tuner status and records from runs
  without a declared metric identity now load (unranked, with the reason)
  instead of failing.

### Fixes

- Authored research-loop runs launched from the console or
  `tools.candidate_operations submit` no longer stop at once with
  `writer_state_refused`: the run's writer-state directory is now prepared
  outside the candidate sandbox and bound into it (#1522).
- An infrastructure abort now stops multi-iteration exploration (exit 3)
  instead of proposing another candidate.
- A task without an output inventory fails before any paid model call.
- Generated validator tests run under a deadline with supervised cleanup.
- A rejected model or loss plugin no longer removes the one already admitted.
- Task plugins reload correctly through equivalent source paths.
- When GPU admission refuses a training phase because it cannot prove the GPU
  environment has room (`environment_headroom_unproven`,
  `measurement_unavailable` or `policy_unavailable`), tuning stops at once and
  records the refusal, instead of spending up to nine more planner calls.
- Inside the run sandbox, GPU phases whose memory need is not yet measured now
  start when the GPU's memory accounting is complete, following the usual trial
  and formal rules. A phase that would exceed the free memory is refused as
  `insufficient_headroom`.
- A research loop no longer fails at its second or later iteration when the
  proposer names an earlier iteration's model as inherited. The claim is kept as
  recorded, and the validator reports it as unverified if the new code does not
  carry it.
- Small tasks no longer lose most training attempts to a false "slowdown"
  check. Steps that take well under a millisecond are timed against a minimum
  wall time, so tiny timing jitter no longer counts as a sustained slowdown.
- The tuning planner is told that `force_formal_round` applies only to the last
  tuning round of each iteration, so it no longer reads it as "every round must
  be formal".
- Tuning logs name the data a round actually uses: a single-file round names
  its file index, and a task-owned round no longer prints a misleading
  "Legacy mode" notice.
- A small training scope no longer fails every round with a batch larger than
  the scope: an unlocked batch size is fitted to the available rows and the fit
  is recorded. A locked batch that does not fit is refused, naming the lock.
- Non-finite values (`inf`, `NaN`) in scores, metric results, records and Data
  Analysis inputs are kept as written instead of turning into `null`, and a
  non-finite score can no longer be retained or reported as a new best.
- A transient GPU sampling failure during admission retries the same phase
  within the remaining attempts (also for protected GPU execution) instead of
  stopping training or replanning the model.
- Completed training is recorded before final validation is admitted, so a
  validation refusal no longer loses the training evidence or overcharges the
  time budget.
- A loss parameter rule that a fixed loss type would make inactive is refused;
  a rule on a field the planner's chosen loss does not use is skipped and
  recorded.
- Proposed training values are checked against the training schema before
  estimation, and a proposal without a segmentation size is no longer lost in
  the advisory estimate.
- Tuner logs, planner history and reflector context show the effective
  configuration when an override replaced the proposal, label the overridden
  text as superseded, and name the knob that actually limited the data
  (`formal_portion`, `trial_portion` or `validation_max_portion`).
- A task plugin's module name now depends only on its content, so the same
  revision gives the same names at any checkout path.
- Python callers of the training entry points must pass a `seed_plan`; models
  are no longer initialized from unseeded random state.
- A configuration that omits `is_trial` now means trial mode everywhere (CLI,
  `WorkflowLaunchConfig`, tuner input), as the CLI already did.
- **Chain launcher flags.** `scripts/launch/run_chain.sh` now accepts and
  forwards `--disclose_execution_constraints` / `--no-disclose_execution_constraints`,
  `--runtime_verification_pathological_min_unit_ms` and
  `--is_trial` / `--no-is_trial` to each iteration. Before, it refused them with
  `Unknown arg`, which blocked the paper workflow launches. Omitting a flag
  keeps the iteration's own default.
- **CSV template on small data.** The template's batch-size rule is now
  `range: {min: 1, max: 32}` instead of `exact: 32`, so a trial round with fewer
  rows than one batch lowers the batch to the row count instead of refusing
  every attempt and ending with `status=no_records`. The planner now chooses the
  batch size up to 32; a proposal above 32 is refused for that attempt. A trial
  round on one or a few rows is weak evidence; more data or larger
  `trial_portion`/`train_portion` give more signal. If you copied the template
  earlier, make the same change in your `task.yaml`. See
  [Small datasets and Trial batches](../../examples/task_templates/csv_classification/README.md#small-datasets-and-trial-batches).

### Integrity and supervision

- **Evidence is re-hashed on every read.** Verification of graph traces,
  judged branches, adaptors and loop records now re-hashes each record when it
  is parsed and does not follow a final symlink, so a record replaced after
  its first check is refused (`graph native record mismatch`).
- **Prompt labels stay on one line.** Literature contribution IDs, contributor
  names, agent and expert-context labels and Data Analysis evidence IDs that
  contain line breaks are quoted, so they cannot forge a heading in a prompt.
- **Parallel runs.** A placed child confirms its host-ledger reservation before
  doing work; failed publication releases the entry; parallel receipts are
  checked for start-after-source-end order; a valid parallel run whose later
  step fails first is no longer refused. A paused loop can be resumed on a
  shared ledger by supplying the resources its root did not declare.
- **Liveness across PID namespaces.** A console restarted in another PID
  namespace no longer releases an operation that is still running.
- **Data Analysis deadlines.** Worker and generated-program supervision now
  count publication and probe time inside the allocation, reap the stopped
  process group without waiting the full grace period, and keep `timed_out`
  when a late orphan is observed.

## Changed behavior for v1.0.0 users

- **Runs started before v1.1.0 cannot be resumed.** The seed contract changed
  (#989, #1078), and the task composition fingerprints and the rendering,
  estimation, verifier, protection and planner assembly identities moved during
  v1.1.0 development (#1313, #1366, #1377, #1411, #1474, #1484, #1486, #1457).
  This also applies to runs started from development builds. Resume compares
  these identities and fails closed; start a new workspace.
- **Stored Data Analysis programs are not reused.** `runtime_environment_identity`
  now also hashes the core supervision modules (#1502), so generated programs
  persisted before the upgrade fail closed on reuse; run Data Analysis again
  in a new workspace.
- **Some judged-branch stamps from 28 to 31 October 2026 no longer verify.**
  Judged and consumed-input stamps written over typed non-finite inputs with
  development builds from that window were hashed with the old encoding
  (#1317, #1400). They fail recomputation; this is a known one-way boundary
  (#1401). Rerun the affected step in a new workspace.
- **Pseudo workspaces from before v1.1.0 cannot be resumed.** Pseudo runs now
  record `validation_max_samples=256` unless set (#1484); an older pseudo
  workspace recorded none, so resume raises `RunInvariantsViolation`. Start a new
  workspace.
- **Real runs need an NVIDIA GPU with CUDA.** Without a visible GPU, a real launch
  exits 2 with a plain message before any model call (#1148, #1164). Dry runs and
  pseudo-mode test runs (no real model calls) are not checked.
- **New default model profile.** Without `--llm_config`, every route now uses
  OpenAI `gpt-5.6-luna` and the native planner, so a clean installation runs
  without extra packages. v1.0.0 used Gemini and needed a planner strategy
  selected explicitly (#706, #1040). Set `OPENAI_API_KEY`, or pass your own
  `--llm_config`. An explicit `--llm_model` keeps its Gemini meaning.
- **`--llm_config` refuses unknown keys at every depth.** A typo or a flat
  `{provider, model_id}` block that v1.0.0 ignored (running on defaults) now fails
  to load and names the key (#1028). Keys starting with `_` are allowed as
  comments.
- **Time budgets** that are zero, negative or non-finite, including
  `bypass_formal_time_budget_minutes=inf`, are refused at launch (#1041).
- **VRAM budget** 0, negative, inf or NaN is refused at launch; omit the flag for
  no ceiling (#1071).
- **Non-finite launch values** (timeouts, safety factors, `target_score`,
  `minimum_boldness`, `degenerate_penalty_score`) are refused at launch (#1070).
- **Parameter rules** that v1.0.0 accepted without effect are refused, naming the
  path: unknown `train_config` paths (#846), unknown `loss_config` fields (#1037),
  `model_config.*` typos or locks naming another model, checked against the model
  that runs, including `--force_model` (#1058), `null` range/allowed/predicate
  rules and coerced bounds such as `true` or `"3"` (#1038), booleans on numeric
  fields (#1060) and non-finite values (#1081).
- **Seed pins `sampling_seed` and `train_base_seed` are retired**; every seed
  derives from `--run_seed`. The `--sampling_seed` flag and saved configurations
  or requests that set either pin are refused (#1020).
- **Unsafe names are refused:** generated model and loss names containing path
  separators (#780) and run names that are not a single safe path component
  (#781, #782).
- **Custom losses** refuse parameters the plugin does not accept, instead of
  silently using its defaults (#720).
- **Watchdog deadlines** now use the smallest explicit phase ceiling
  (`budget-ceiling-v1`); enabling the watchdog without a finite ceiling is
  refused before setup.
  `--runtime_watchdog_deadline_policy forecast-tightening-v1` selects the old
  rule (#692).
- **No universal batch-size × segment-size ceiling.** v1.0.0 rejected inputs above
  800,000; a selected preflight estimator profile can still declare a limit
  (#690).
- **Research-agent prompts changed.** They now disclose execution constraints
  (#724, #726), prioritize human advice within declared task and parameter locks
  (#929), and align generated model proposals with implementation defaults
  (#758). Results are not directly comparable with v1.0.0 runs.

### If you ran the console from an unreleased development build

Existing `console.json` files keep working. Workflows listed under
`editor_projects` appear under their matching task or **Other workflows (no
configured task)**. `check` refuses manifest references the run sandbox does not
mount and warns about unusable GPU devices. The missing-`/sys` warning is gone,
because GPU runs now mount `/sys` themselves; an entry that lists `"/sys"` in
`task_read_only` keeps working. New operation
records may carry `setup_id`, which older builds refuse. A page that reviewed a
run before the upgrade gets `stale_review` once; review again. Formal-delta
settings on the candidate path are refused, the Seed input is in step 2,
abbreviated protected native-chain flags such as `--run_` are refused, and new
no-GPU records carry a longer `probe_capability_reason`. A saved workflow with
Trial/formal mode off is now refused for a non-TIDMAD task; turn the mode on.
The Validate step's advice input now uses the `optional.advice-text` contract
(shown as "Advice text"); authored advice bindings and custom adaptor manifests
that used `optional.text` for advice must change the contract id. Monitor
remembers the last operation per operations store; the old global browser key
is ignored. A shared host budget without `max_queued_operations` no longer lets
submissions wait: the default is 0, and a run that cannot start at once is
refused with `host_queue_full`. Set a positive value to allow waiting (#1329).

## Reproducing the paper

The settings used for the [SIDERIUS paper (arXiv:2610.14024)](https://arxiv.org/abs/2610.14024)
are kept as versioned configuration in
[siderius-exp](https://github.com/yuema137/siderius-exp), not as SIDERIUS
defaults. Use that configuration to reproduce paper results; the v1.1.0 defaults
and templates are starting points for new work. Paper reproduction keeps its
historical framework pin in siderius-exp; it does not run on v1.1.0 by default.
Because the assembly identities above moved, siderius-exp qualified the
v1.1.0 identities in its own versioned compatibility configuration and pins this
release (see its `experiments/shared/v110-compatibility.md`). On v1.1.0 the paper
prompts are byte-identical to the original captures except the planner startup
block listed under Known limitations; for exact paper reproduction, use the
historical pin.

## Known limitations

- **No CPU mode.** Steps before launch work on CPU, but real runs need a GPU. A
  CPU small-trial mode is on the roadmap (#1146).
- **GPU memory inside the run sandbox is counted conservatively.** The sandbox
  cannot tell which GPU memory belongs to its own run, so admission counts all
  memory in use on the GPU as used by other processes. A run can be refused on a
  GPU that has room for it. A host-side observer is planned (#1180).
- **Evaluation scope in 1.1.** Constraints, measurements and rubrics run on
  the native task-owned scoring route only; anchor-normalized scoring and an
  external `CandidateEvaluationExecutor` refuse them at launch. Rubrics guide
  the agents but no framework step judges candidates against them (judged
  selection is a follow-up). Measurements are the four built-ins; custom
  measurement plugins, FLOPs and external hardware are follow-ups. A
  candidate that violates a constraint loses its score in the record; the raw
  value stays in `evaluation_result`.
- **TIDMAD's default pseudo run is refused.** With the 256-row pseudo ceiling,
  TIDMAD's evaluation scope keeps only its first file, so its Health checks
  cannot be covered and the run refuses up front with `TaskHealthCoverageError`.
  Workaround: `--formal_eval_portion 0.01 --validation_max_samples 10000`. The
  fix belongs to the task, in siderius-exp.
- **A small trial scope under an `exact` batch-size lock still fails quietly.**
  On another task with an exact lock, a trial round can still have fewer rows
  than one batch; each attempt is refused, failed rounds do not advance to the
  formal round, and the run ends with `status=no_records` and exit 0 (by
  contract). Use a `range` rule, as the CSV template does. A framework fix is
  tracked in #1508.
- **Paper planner startup requests differ by one block.** With execution-
  constraint disclosure disabled, the planner's first request still carries the
  `[CURRENT RUN EXECUTION CONSTRAINTS]` "Incomplete constraint information"
  block (about 1,461 characters). The four paper planner startup requests (TESS,
  LIGO, Project8, TIDMAD) therefore differ from the original captures by exactly
  that block; all other paper prompts are byte-identical. siderius-exp asserts
  this exact difference. A fix is planned (#1510).
- **One out-of-range planner field resets every trial field.** If the planner
  proposes a trial field outside its range (for example `train_portion` below
  0.01), all trial fields fall back to their defaults and the planner is not
  told why. With a tight trial budget it can repeat a workload that runtime
  admission refuses until the attempts run out, and the iteration ends with
  `status=no_records`. The log line `LLM returned invalid trial fields —
  falling back to defaults` marks it. Scores are not affected. A fix is planned
  (#1513).
- **Formal tuning rounds outside the templates use 10% of the rows.** The
  framework default `formal_portion` is still 0.1; the templates and examples
  set 1.0. Set `formal_portion` in your workflow for a small task.
- **No time-based stop condition.** A loop cannot yet stop or pause after a set
  time without improvement; bound time with training budgets and the iteration
  limit (#1231).
- **A research loop and a literature review merged by an LLM judge cannot be in
  one workflow.** Run them in two steps: first the literature-judged workflow,
  then the loop, giving the merged findings to the proposer as advice. The
  [setup guidance](../agent-reference/siderius-setup-review/SKILL.md) shows how.
- **Example bundle download.** If the v1.1.0 release page lists
  `siderius-example-quickstart-1.1.0.zip`, download it; otherwise build it from
  your checkout as the [example bundle guide](../../examples/console_bundle/README.md)
  shows.
- The judged profiles are chosen through workflow/run configuration, not from the
  console; the judged proposal profile does not run training, loops or routes.
- Parallel steps are opt-in; native chains and preparation stay serial. Each
  run's GPU reservation uses one GPU; multi-GPU reservations are planned for v1.2.
- A fixed seed does not guarantee bitwise-identical GPU results or identical LLM
  decisions.
- The console reads new tasks and saved model/data settings when it restarts. A
  global advice file does not change workflows that carry their own advice.
- A native chain captured with `CUDA_VISIBLE_DEVICES=''` on a GPU host can be
  refused with `hardware_identity_changed` when it is launched detached or
  resumed (#1451).

## Upgrade steps

1. Finish or stop any run started before v1.1.0, including runs from
   development builds; after upgrading, start new runs in a new workspace.
2. Update your checkout to v1.1.0 and run `uv sync --group dev --frozen` in it.
3. Check your `--llm_config`, parameter rules and budgets against
   [Changed behavior](#changed-behavior-for-v100-users). Each refusal names the
   setting to fix. Most are checked at launch, before any model call; rules on a
   model the planner chooses are checked when it plans, after its model calls.
4. To work with your coding agent, follow
   [getting started](../getting-started/README.md). To try the experimental
   console, follow the
   [first-hour path](../getting-started/README.md#your-first-hour-from-the-example-to-your-own-task).
   A `console.json` you write yourself (not created by `init`) needs
   `workspace_root` and `"experiment_setups": {"browser_creatable": true}` to
   create setups in the browser or to use `add-task --from-bundle`.
