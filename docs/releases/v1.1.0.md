# SIDERIUS v1.1.0

This release adds a browser workspace for preparing, editing and monitoring
research runs, more workflow choices, and a recorded run seed across native
execution. Read the upgrade restrictions below before continuing existing work.

## Changes

### Browser console and GUI

- Edit supported workflows on a visual canvas, connect typed inputs, use
  templates, and review Python source changes before saving. Named versions,
  restore and clearer conflict messages help keep browser and file edits aligned.
- Follow the Run page from preparation through optional settings and launch.
  Quick start guides initial setup; Monitor shows recorded outcomes, logs and
  loop control requests, with clearer connection and failure messages.
- Use the global Settings page to select model profiles, advice files and data
  folders, upload profile/advice files, and export a workflow's model profile and
  inline advice for CLI use.
- Set an optional run Seed and read back the recorded value. Add a JudgeStop
  condition in the loop editor and inspect its recorded verdicts in Monitor.

### Workflows

- Declare conditional routes, including a supported fallback branch when the
  first validator rejects a candidate.
- Use deterministic adaptors to combine, select and distribute results within
  supported profiles. Literature profiles can collect multiple reviews or split
  ranked findings across proposals.
- Choose LLM combining strategies: `rubric-rank/v1`, `debate-judge/v1`,
  `primary-advisors-llm/v1` and `judge-merge/v1`.
- Run `native-literature-judged/v1` and `native-proposal-judged/v1` through
  CLI/preview configuration. These profiles apply LLM strategies to reviews or
  proposals, with bounded judge calls and recorded evidence that can be verified
  without calling the provider again.

### JudgeStop

Authored loops can ask an LLM whether to stop after a configured number of
completed bodies. Deterministic stop conditions take precedence. The operator
controls judge routing and the call cap; the workflow declares the criterion
and whether a judge failure ends the loop or records an abstention and continues.

### Reproducibility

The run seed contract (S1–S8) records an operator-supplied or generated seed and
locks it for continuation. Stable, purpose-specific seeds cover training,
tuner attempts, analysis sampling and programs, and validation probes. Candidate
operations, native chains and the console carry the seed through admission and
readback. A regression guard checks for new unaccounted random-number sources;
generated-code seed calls are recorded for inspection.

### Resource scheduling

Candidate operations can share an operator-declared host budget through a
reservation ledger. Operations that fit the budget but cannot currently be placed
wait in submission order; queued operations can be cancelled before execution.
Reservations also account for a graph's declared peak resource demand.

### Fixes

- The default LLM profile selects the native planner on a clean installation.
- Generated validator tests respect a declared deadline and have supervised
  process cleanup; candidate records handle non-finite results consistently.
- Settings reject duplicate JSON keys, rejected browser hosts show the allowed
  console URL, and task plugins reload correctly through equivalent source paths.
- Authored validation joins can bind the existing `human_advice` argument.

## Behaviour changes

- Workspaces started with v1.0.0 cannot be resumed after upgrading to v1.1.0, because the planner identity and seed contract changed. Finish or restart in-progress runs before upgrading, and start new work in v1.1.0.
- An operator VRAM budget of 0, a negative value, inf or NaN is now refused at launch. Omit the flag for no ceiling.
- Non-finite launch values (timeouts, safety factors, target_score, minimum_boldness, degenerate_penalty_score) are refused at launch.
- Formal-delta settings on the candidate path are refused as inactive (CLI unchanged).
- The console Seed input moved to step 2 "Optional settings"; preparation (step 1) generates and records its own seed.

## Scope and limitations

LLM-judged profiles are chosen through workflow/run configuration, not yet from
the console run picker. The judged proposal profile does not admit training,
loops or routes. Resource-envelope support has landed, but graph units still
dispatch serially; concurrent dispatch is separate work. A GPU envelope reserves
one GPU, not multiple GPUs. A fixed seed alone does not guarantee bitwise-identical
GPU results or identical LLM decisions. Saved model/data settings take effect
after a console server restart; selecting a global advice file does not apply it
to workflows, which retain their own advice.

See the [console guide](../../src/tools/candidate_console/README.md),
[worker profile contract](../../src/tools/candidate_worker/candidate-worker-contract.md)
and [seed contract](../agent-reference/mechanisms/seeding.md) for supported
configuration and execution boundaries.
