# SIDERIUS v1.1.0

This release adds a **browser console** for building, running and monitoring
research workflows, a ready example and a CSV task template to start from,
research loops you can pause, steer and resume, a recorded run seed, and more
LLM providers and workflow choices.

**Before upgrading from v1.0.0:** runs started with v1.0.0 cannot be resumed
with v1.1.0, real runs now require an NVIDIA GPU, and several malformed settings
that v1.0.0 silently ignored are now refused. Read
[Changed behavior](#changed-behavior-for-v100-users) first.

## What's new

### Browser console

The console is new in v1.1.0. You create a private workspace with `init`,
register a task with `add-task`, start the console with `serve` and open it in a
browser, locally or through an SSH tunnel. The
[console guide](../../src/tools/candidate_console/README.md) covers each step.

- **Task, experiment setup, run.** Tabs **Home · Task · Workflow · Run · Monitor
  · Settings**. The Task tab summarizes the chosen task (data, model
  input/output, objective, main score, Health checks, plugins, locked parameters,
  deliverable). Model input and output shows each input and output with its
  shape and meaning, the classes and the task type. An experiment setup is one
  workflow for one task; each run belongs to one setup and is listed under it.
- **GPU detection and GPU runs.** `add-task` finds this machine's NVIDIA GPUs
  (`/dev/nvidia<N>`) and gives them to the task's runs without asking;
  `--no-gpu` gives none and `--device PATH ...` gives exactly the paths you
  name. For a GPU task, the run sandbox mounts the host's `/sys` read-only and
  passes the NVIDIA control devices automatically, which CUDA needs to start.
  `check --gpu` starts CUDA inside that same sandbox and prints
  `GPU PASS` or `GPU FAIL` with the cause, so you can test a task before
  launching.
- **Workflow editor.** Build a workflow on a visual canvas from templates or a
  blank start, connect typed inputs and outputs, and review the Python source
  change before saving. Named versions, undo/redo and restore are included.
  **Fit** frames the whole graph, and Training settings explains Trial and
  Formal rounds.
- **Template defaults.** Templates start in trial mode, with **Health checks**
  set to Block on failure and **Result standing** set to Scientific, so the
  task's blocking checks can invalidate a round and Health-valid results count
  toward the run's best score. The Train & tune step has a **Trial/formal mode**
  control.
- **Run and Monitor.** Prepare, review and launch a run, set an optional run
  seed, and follow results, logs and reported token use per model. Run review
  lists the advice, Health mode, training budgets, epoch ceilings and task locks
  the run will use, and the setup's run list updates after Launch. Failed
  preparations or launches are named with their cause and log file. Monitor
  shows a **Train & tune outcome** row; a step that completed no rounds never
  reads as succeeded. **Stop run** cancels a running candidate. Launched runs
  keep running if you stop the console server; start it again to keep
  monitoring them.
- **Untrainable runs are refused before spending.** With **Trial/formal mode**
  off, every round uses single-file mode, which only tasks with TIDMAD-style
  data can train in. Run review, training admission and tuner startup refuse
  such a run for any other task, with the cause, before any model call.
- **Research loops.** A workflow can repeat its research round a fixed number of
  times, using the previous round's results. Stop or pause a loop between rounds
  and resume the same run. Stop conditions (metric threshold, no improvement, an
  LLM judge) can end the loop, or with **Pause and ask me** pause it and say why.
  When you resume, you can add advice for the next rounds. **End loop here**
  ends a paused loop instead of resuming it, and Monitor then reads "Ended by
  you at the pause after body N".
- **Settings and credentials.** Choose model profiles, advice files and data
  folders in the browser. The console reads API keys from a mode-600 JSON or
  dotenv file and never prints them. Light and dark themes are available.
- **Clear errors.** `init`, `check` and `serve` name each invalid
  `console.json` field and the error type (never the value), and name a missing
  manifest, model profile or workflow file with its configured path. When the
  workspace's parent folder is writable by group or others, `init` says so and
  prints the fix, `chmod 700 <path>`.

### Start from an example, then package your own task

- The [first-hour path](../getting-started/README.md#your-first-hour-from-the-example-to-your-own-task)
  goes from install to a first console run, then to your own task, with the
  output to expect at each step.
- The **example bundle** `siderius-example-quickstart-1.1.0.zip` holds a small
  synthetic task and a ready experiment setup; `add-task --from-bundle` verifies
  and registers it. See the [example bundle guide](../../examples/console_bundle/README.md).
- The [CSV classification template](../../examples/task_templates/csv_classification/README.md)
  is a complete task package for `train.csv` / `validation.csv` data, with a
  metric, Health checks, a reference model and `EDIT HERE` markers.

### Command line and workflows

- **Run seed.** Each run records one seed, given with `--run_seed` or generated,
  and every training, sampling and validation seed derives from it. A resumed run
  must use the same seed. See the [seed contract](../agent-reference/mechanisms/seeding.md).
- **LLM providers and profiles.** Anthropic, Moonshot/Kimi and Z.AI/GLM are
  available through the optional `pydantic-ai` extra. The opt-in profile
  `configs/llm/openai-moderate-v1.json` is recommended for research runs.
- **Training.** Native training can run explicit cosine or step learning-rate
  schedules (off by default), and epoch caps above 100 are now accepted.
- **Workflow choices.** Conditional routes with a fallback branch; deterministic
  steps that combine, select or distribute results; LLM combining strategies
  (`rubric-rank/v1`, `debate-judge/v1`, `primary-advisors-llm/v1`,
  `judge-merge/v1`); and the judged profiles `native-literature-judged/v1` and
  `native-proposal-judged/v1`, whose judge calls are bounded and recorded.
- **Shared GPU budgets and parallel steps.** Runs can share an operator-declared
  host budget; runs that do not fit yet wait in order. Independent workflow steps
  can run in parallel within the budget. See
  [Share one GPU budget](../../src/tools/candidate_operations/README.md#share-one-gpu-budget-across-operations).
- **Custom combining steps** can be checked, self-tested and admitted with
  `.venv/bin/python -m tools.adaptors`; running them inside workflows comes in a later
  release.
- The standard chain launcher accepts `--gpu_execution_policy_json`, so a GPU
  execution policy file reaches every iteration of a chain.
- The CLI reports which `.env` file it loaded and warns when that file is
  outside the checkout, readable by others, or holds an empty key.

### Fixes

- An infrastructure abort now stops multi-iteration exploration (exit 3)
  instead of proposing another candidate.
- A task without an output inventory fails before any paid model call.
- Generated validator tests run under a deadline with supervised cleanup.
- A rejected model or loss plugin no longer removes the one already admitted.
- Task plugins reload correctly through equivalent source paths.
- When GPU admission refuses a training phase because it cannot prove the GPU
  environment has room (`environment_headroom_unproven`,
  `measurement_unavailable` or `policy_unavailable`), tuning stops at once and
  records the refusal, instead of spending up to nine more planner calls.
- Inside the run sandbox, GPU phases whose memory need is not yet measured now
  start when the GPU's memory accounting is complete, following the usual trial
  and formal rules. A phase that would exceed the free memory is refused as
  `insufficient_headroom`.
- A research loop no longer fails at its second or later body when the proposer
  names an earlier body's model as inherited. The claim is kept as recorded,
  and the validator reports it as unverified if the new code does not carry it.

## Changed behavior for v1.0.0 users

- **Runs from v1.0.0 cannot be resumed.** The seed contract and the native
  planner's identity changed (#989, #1078). Finish or restart in-progress runs
  before upgrading and start new work in v1.1.0.
- **Real runs need an NVIDIA GPU with CUDA.** Without a visible GPU, a real launch
  exits 2 with a plain message before any model call (#1148, #1164). Dry runs and
  pseudo-mode test runs (no real model calls) are not checked.
- **New default model profile.** Without `--llm_config`, every route now uses
  OpenAI `gpt-5.6-luna` and the native planner, so a clean installation runs
  without extra packages. v1.0.0 used Gemini and needed a planner strategy
  selected explicitly (#706, #1040). Set `OPENAI_API_KEY`, or pass your own
  `--llm_config`. An explicit `--llm_model` keeps its Gemini meaning.
- **`--llm_config` refuses unknown keys at every depth.** A typo or a flat
  `{provider, model_id}` block that v1.0.0 ignored (running on defaults) now fails
  to load and names the key (#1028). Keys starting with `_` are allowed as
  comments.
- **Time budgets** that are zero, negative or non-finite, including
  `bypass_formal_time_budget_minutes=inf`, are refused at launch (#1041).
- **VRAM budget** 0, negative, inf or NaN is refused at launch; omit the flag for
  no ceiling (#1071).
- **Non-finite launch values** (timeouts, safety factors, `target_score`,
  `minimum_boldness`, `degenerate_penalty_score`) are refused at launch (#1070).
- **Parameter rules** that v1.0.0 accepted without effect are refused, naming the
  path: unknown `train_config` paths (#846), unknown `loss_config` fields (#1037),
  `model_config.*` typos or locks naming another model, checked against the model
  that runs, including `--force_model` (#1058), `null` range/allowed/predicate
  rules and coerced bounds such as `true` or `"3"` (#1038), booleans on numeric
  fields (#1060) and non-finite values (#1081).
- **Seed pins `sampling_seed` and `train_base_seed` are retired**; every seed
  derives from `--run_seed`. The `--sampling_seed` flag and saved configurations
  or requests that set either pin are refused (#1020).
- **Unsafe names are refused:** generated model and loss names containing path
  separators (#780) and run names that are not a single safe path component
  (#781, #782).
- **Custom losses** refuse parameters the plugin does not accept, instead of
  silently using its defaults (#720).
- **Watchdog deadlines** now use the smallest explicit phase ceiling
  (`budget-ceiling-v1`); enabling the watchdog without a finite ceiling is
  refused before setup.
  `--runtime_watchdog_deadline_policy forecast-tightening-v1` selects the old
  rule (#692).
- **No universal batch-size × segment-size ceiling.** v1.0.0 rejected inputs above
  800,000; a selected preflight estimator profile can still declare a limit
  (#690).
- **Research-agent prompts changed.** They now disclose execution constraints
  (#724, #726), prioritize human advice within declared task and parameter locks
  (#929), and align generated model proposals with implementation defaults
  (#758). Results are not directly comparable with v1.0.0 runs.

### If you ran the console from an unreleased development build

Existing `console.json` files keep working. Workflows listed under
`editor_projects` appear under their matching task or **Other workflows (no
configured task)**. `check` refuses manifest references the run sandbox does not
mount and warns about unusable GPU devices. The missing-`/sys` warning is gone,
because GPU runs now mount `/sys` themselves; an entry that lists `"/sys"` in
`task_read_only` keeps working. New operation
records may carry `setup_id`, which older builds refuse. A page that reviewed a
run before the upgrade gets `stale_review` once; review again. Formal-delta
settings on the candidate path are refused, the Seed input is in step 2,
abbreviated protected native-chain flags such as `--run_` are refused, and new
no-GPU records carry a longer `probe_capability_reason`. A saved workflow with
Trial/formal mode off is now refused for a non-TIDMAD task; turn the mode on.

## Known limitations

- **No CPU mode.** Steps before launch work on CPU, but real runs need a GPU. A
  CPU small-trial mode is on the roadmap (#1146).
- **GPU memory inside the run sandbox is counted conservatively.** The sandbox
  cannot tell which GPU memory belongs to its own run, so admission counts all
  memory in use on the GPU as used by other processes. A run can be refused on a
  GPU that has room for it. A host-side observer is planned (#1180).
- **Short training steps can fail runtime checks.** On small tasks whose units
  take well under a millisecond, the "pathological sustained slowdown" check can
  end most attempts as `skipped_time_risk` (#1197).
- **Short loops train on a 10% sample.** With trial mode on, short loops run
  every round as a formal round on 10% of the rows (`formal_portion` 0.1), and
  the trial budgets go unused (#1200).
- **Example bundle download.** If the v1.1.0 release page lists
  `siderius-example-quickstart-1.1.0.zip`, download it; otherwise build it from
  your checkout as the [example bundle guide](../../examples/console_bundle/README.md)
  shows.
- The judged profiles are chosen through workflow/run configuration, not from the
  console; the judged proposal profile does not run training, loops or routes.
- Parallel steps are opt-in; native chains and preparation stay serial. Each
  run's GPU reservation uses one GPU; multi-GPU reservations are planned for v1.2.
- A fixed seed does not guarantee bitwise-identical GPU results or identical LLM
  decisions.
- The console reads new tasks and saved model/data settings when it restarts. A
  global advice file does not change workflows that carry their own advice.

## Upgrade steps

1. Finish or stop any run started with v1.0.0.
2. Update your checkout to v1.1.0 and run `uv sync --group dev --frozen` in it.
3. Check your `--llm_config`, parameter rules and budgets against
   [Changed behavior](#changed-behavior-for-v100-users). Each refusal names the
   setting to fix. Most are checked at launch, before any model call; rules on a
   model the planner chooses are checked when it plans, after its model calls.
4. To use the console, follow the
   [first-hour path](../getting-started/README.md#your-first-hour-from-the-example-to-your-own-task).
   A `console.json` you write yourself (not created by `init`) needs
   `workspace_root` and `"experiment_setups": {"browser_creatable": true}` to
   create setups in the browser or to use `add-task --from-bundle`.
