# SIDERIUS v1.1.0

This release adds a browser console organized around three things (a **task**,
the **experiment setups** built for it, and their **runs**), a downloadable
example to start from, a template for packaging your own CSV data, research
loops that can pause and ask for your advice, more workflow choices, and a
recorded run seed. Real runs need an NVIDIA GPU.

**Before upgrading:** workspaces started with v1.0.0 cannot be resumed with
v1.1.0. Finish or restart in-progress runs first; see
[Upgrade steps](#upgrade-steps).

## What's new

### Task, experiment setup and run in the console

- The console now has the tabs **Home · Task · Workflow · Run · Monitor ·
  Settings**. Choose a task first; Workflow and Run open only after a task is
  chosen (selected automatically when only one task is configured).
- The **Task** tab shows a read-only summary of the chosen task: data folder and
  size, model input/output, objective, main score and recording metrics, Health
  checks (Blocking / Recording), plugins, locked parameters, deliverable and run
  policy. **Count samples** counts the declared training and evaluation splits.
  Task code runs only in the sandboxed composition child, never in the console.
- An **experiment setup** is one workflow for one task. On **Workflow**, select
  **New setup…** to create one from a template or blank. Setups are stored in
  `siderius_workspace/settings/experiment_setups.json` and
  `siderius_workspace/projects/<setup id>/workflow.py`.
- Each run records the setup it belongs to. The Run page names "Setup: … · Task:
  …" and lists **Runs of this setup**, each linking to Monitor.
- **Quick start** walks through choosing a task, then creating a setup from the
  research-loop template or opening an existing one.

### Start from an example, then package your own task

- **Example bundle.** `siderius-example-quickstart-1.1.0.zip` holds a small
  synthetic task package and a ready experiment setup. Build it with
  `.venv/bin/python -m tools.release.build_example_bundle --output-dir DIR`
  (the version defaults to the one in `pyproject.toml`), then register it with
  `add-task --from-bundle DIR`, which verifies `SHA256SUMS` before copying.
- **Register a task** with
  `python -m tools.candidate_console add-task --config … --manifest …`. It
  writes the task entry into `console.json`, mounts the package folder
  `siderius_workspace/tasks/<name>/` read-only for runs, refuses references the
  run sandbox cannot read, and runs `check`. `init` now creates `tasks/`.
- **Credentials at init.** `init --credential-file PATH` records your mode-600
  key file in a new `console.json`. It checks the file without opening it and
  never prints its contents.
- **First-hour path.** The
  [getting-started guide](../getting-started/README.md#your-first-hour-from-the-example-to-your-own-task)
  gives every command, from install to a first console run and then your own
  task, with the output to expect.
- **CSV classification template.**
  [`examples/task_templates/csv_classification/`](../../examples/task_templates/csv_classification/README.md)
  is a complete task package for `train.csv` / `validation.csv` data, with a
  balanced-accuracy metric, Health checks, a reference model and `EDIT HERE`
  markers.
- The connect card and the `init` / `check` / `serve` output explain the
  console address, where the access token is and when to use an SSH tunnel.

### Research loops: pause and ask, resume with advice

- A loop stop condition (metric threshold, no improvement, JudgeStop) can be set
  to **When met: Pause and ask me** instead of **Stop**. Monitor then says why the
  loop is waiting, for example "No improvement for 3 bodies … Paused after body 7
  of 12."
- Resume a paused loop with your advice: type it after **Review resume** in
  Monitor, or pass `write-loop-resume --advice-file FILE` on the CLI. Only the
  proposer receives it, for the bodies of that resumed segment; the recorded
  advice is verified on readback.
- Authored loops can ask an LLM whether to stop (JudgeStop) after a configured
  number of completed bodies. Deterministic stop conditions take precedence.

### Browser console and GUI

- Edit supported workflows on a visual canvas, connect typed inputs, use
  templates (with larger, readable previews), and review Python source changes
  before saving. Named versions, restore and clearer conflict messages keep
  browser and file edits aligned.
- Follow the Run page from preparation through optional settings and launch.
  When preparation or launch fails, the Run page says so, shows the cause and
  names the log to open (`inputs/preparation/worker.log` for preparation).
- The global **Settings** page selects model profiles, advice files and data
  folders, uploads profile/advice files, and exports a workflow's model profile
  and inline advice for CLI use.
- Set an optional run **Seed** and read back the recorded value.
- The console states that the first research round starts cold: no earlier
  results are needed.

### Workflows

- Declare conditional routes, including a fallback branch when the first
  validator rejects a candidate.
- Deterministic adaptors combine, select and distribute results within supported
  profiles. Literature profiles can collect multiple reviews or split ranked
  findings across proposals.
- LLM combining strategies: `rubric-rank/v1`, `debate-judge/v1`,
  `primary-advisors-llm/v1` and `judge-merge/v1`.
- `native-literature-judged/v1` and `native-proposal-judged/v1` apply these
  strategies to reviews or proposals through CLI/preview configuration, with
  bounded judge calls and recorded evidence that can be verified without calling
  the provider again.

### Reproducibility

The run seed contract records an operator-supplied or generated seed and locks
it for continuation. Purpose-specific seeds derived from it cover training,
tuner attempts, analysis sampling and programs, and validation probes. Candidate
operations, native chains and the console carry the seed through admission and
readback. Generated-code seed calls are recorded for inspection.

### Resource scheduling

- Candidate operations can share an operator-declared host budget through a
  reservation ledger. Operations that fit but cannot be placed yet wait in
  submission order and can be cancelled before they start.
- Set the run request's `parallel` field to dispatch independent graph units
  concurrently within the declared budget. When the peak demand does not fit the
  host but individual units do, the run proceeds with less concurrency.
- With a host ledger configured, the Run page's **Host resources and parallel
  nodes** panel declares run resources and per-capability parallel settings.

### Fixes

- The default LLM profile selects the native planner on a clean installation.
- Generated validator tests respect a declared deadline and have supervised
  process cleanup; candidate records handle non-finite results consistently.
- Settings reject duplicate JSON keys, rejected browser hosts show the allowed
  console URL, and task plugins reload correctly through equivalent source paths.
- Authored validation joins can bind the existing `human_advice` argument.
- Each validation unit runs the protocol its node declares.
- `max_steps_per_attempt` again prices attempts for tasks whose data path
  requires a seed when counting training rows.

## Changed behavior and compatibility

- **v1.0.0 workspaces are not resumable.** The native planner's identity moved
  and the seed contract changed, so a run started with v1.0.0 cannot be resumed
  with v1.1.0. Finish or restart in-progress runs before upgrading and start new
  work in v1.1.0.
- An operator VRAM budget of 0, a negative value, inf or NaN is refused at
  launch. Omit the flag for no ceiling.
- Non-finite launch values (timeouts, safety factors, `target_score`,
  `minimum_boldness`, `degenerate_penalty_score`) are refused at launch.
- Formal-delta settings on the candidate path are refused as inactive (the CLI is
  unchanged).
- The console **Seed** input moved to step 2 "Optional settings"; preparation
  (step 1) generates and records its own seed.
- **Real runs need an NVIDIA GPU with CUDA.** A real CLI launch without a visible
  GPU now exits 2 with a plain message before any model call, run lock or
  iteration folder. Pseudo runs and dry runs are not checked. Run review in the
  console shows "Compute: NVIDIA GPU required" for workflows that train.
- Native-chain declarations refuse abbreviated or ambiguous forms of protected
  CLI controls (for example `--run_`). Saved captures that carry such aliases
  now fail declaration validation.
- `check` and console startup refuse a task whose manifest references a file the
  run sandbox does not mount, naming the file. Such a task would already have
  failed during preparation.
- `check` and `serve` warn when GPU device nodes are passed without `/sys` in
  `task_read_only`, and about device paths the sandbox cannot pass. `add-task`
  refuses such device paths.
- Existing `console.json` files keep working. Older workflows listed under
  `editor_projects` appear under the task they match, or under **Other workflows
  (no configured task)**. Creating setups in the browser needs
  `"experiment_setups": {"browser_creatable": true}` in `console.json`; `init`
  writes it only into a new file.
- A console with no configured task, or several tasks and none chosen, opens
  Workflow and Run only after a task is chosen.
- New operation records may carry `setup_id`; older SIDERIUS builds refuse to
  read them. Records without it are unchanged. A browser page that reviewed a
  run before the upgrade gets `stale_review` once at launch; review again.
- New tuner records written on a host without a usable GPU carry a longer,
  cause-specific `probe_capability_reason`; existing records are unchanged.

## Known limitations

- **No CPU mode.** Real runs require an NVIDIA GPU; steps before launch work on
  CPU. An explicit CPU small-trial mode is on the roadmap (#1146).
- **GPU runs from the console** need `/sys` readable inside the run sandbox, in
  addition to the `/dev/nvidia*` device nodes; `add-task` does not add it. See
  **GPU runs** in
  [Set up and open the console](../../src/tools/candidate_console/README.md#set-up-and-open-the-console).
- The example bundle zip is published as an asset of the v1.1.0 release; until
  then, build it from your checkout as shown in the
  [example bundle guide](../../examples/console_bundle/README.md).
- LLM-judged profiles are chosen through workflow/run configuration, not from the
  console run picker. The judged proposal profile does not admit training, loops
  or routes.
- Parallel graph dispatch is opt-in; native chains and preparation remain serial
  and are not reserved in the host ledger. Under that ledger each run's GPU
  reservation uses one GPU; multi-GPU reservations are planned for v1.2.
- A fixed seed alone does not guarantee bitwise-identical GPU results or
  identical LLM decisions.
- Saved model/data settings and new tasks take effect after a console restart.
  Selecting a global advice file does not apply it to workflows, which keep their
  own advice.

See the [console guide](../../src/tools/candidate_console/README.md),
[worker profile contract](../../src/tools/candidate_worker/candidate-worker-contract.md)
and [seed contract](../agent-reference/mechanisms/seeding.md) for supported
configuration and execution boundaries.

## Upgrade steps

1. Finish or stop any run started with v1.0.0. It cannot be resumed after the
   upgrade.
2. Update your checkout to v1.1.0 and reinstall in that checkout:
   `uv sync --group dev --frozen`.
3. For an existing console workspace, run
   `.venv/bin/python -m tools.candidate_console check --config <workspace>/settings/console.json`.
   Fix any refused file reference (move the file into the task package, or
   register the package with `add-task`) and read any GPU warning.
4. To create experiment setups in the browser, add
   `"experiment_setups": {"browser_creatable": true}` to an existing
   `console.json`.
5. Restart the console and reload the browser page. Start new runs; if a launch
   reports `stale_review`, review it again.
